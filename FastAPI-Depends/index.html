Patrones Avanzados y Mejores Prácticas

Introducción

Ya sabes que Depends es el corazón del sistema de inyección de dependencias de FastAPI. Es lo que nos permite tener bases de datos, autenticación y configuraciones de forma limpia.

Pero Depends es mucho más que obtener una sesión de base de datos. Vamos a explorar los patrones avanzados que separan una API funcional de una API robusta, mantenible y testeable.

1. El Secreto de use_cache=True

Por defecto, FastAPI cachea el resultado de una dependencia dentro del mismo request. Si múltiples dependencias en la misma cadena de llamadas dependen de get_db, FastAPI solo la ejecutará una vez.

Esto es casi siempre lo que quieres. Pero, ¿y si no? El parámetro use_cache=False fuerza a FastAPI a re-ejecutar la dependencia cada vez que es llamada, incluso dentro del mismo request.

Caso de uso avanzado: Necesitas un objeto de transacción de base de datos completamente nuevo y aislado para una parte específica de tu lógica, separado de la sesión principal. 


from fastapi import FastAPI, Depends

app = FastAPI()

def get_fresh_transaction_id() -> str:
    # Imagina que esto genera un ID de transacción único
    import time
    return f"tx-{int(time.time_ns())}"

# Esta dependencia se ejecutará CADA VEZ que se inyecte
def get_new_tx_id(tx_id: str = Depends(get_fresh_transaction_id, use_cache=False)):
    return tx_id

# Esta dependencia se cacheará (comportamiento normal)
def get_cached_tx_id(tx_id: str = Depends(get_fresh_transaction_id, use_cache=True)):
    return tx_id

@app.get("/cache-demo")
async def cache_demo(
    tx1: str = Depends(get_new_tx_id),      # Se ejecuta get_fresh_transaction_id
    tx2: str = Depends(get_new_tx_id),      # Se ejecuta OTRA VEZ
    tx3: str = Depends(get_cached_tx_id),   # Se ejecuta get_fresh_transaction_id
    tx4: str = Depends(get_cached_tx_id)    # USA EL VALOR CACHEADO de tx3
):
    # tx1 y tx2 serán diferentes
    # tx3 y tx4 serán iguales
    return {"tx1": tx1, "tx2": tx2, "tx3": tx3, "tx4": tx4}

2. Gestión Avanzada de Recursos con yield

El patrón yield es la forma canónica de manejar recursos que necesitan limpieza (setup y teardown), como sesiones de base de datos o conexiones a servicios externos.

El código antes de yield se ejecuta antes de pasar el control al *path operation*. El código después de yield (usualmente en un bloque finally) se ejecuta *después* de que el *path operation* ha terminado, incluso si ha fallado.

Mejor práctica: Usa esto para hacer commit o rollback de transacciones de base de datos automáticamente. 


from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session
# Asume que db_session, Base, engine están definidos en alguna parte
# from .database import SessionLocal

# Simulación de la sesión de DB
class DBSession:
    def __init__(self): self.commited = False; self.rolled_back = False
    def commit(self): self.commited = True
    def rollback(self): self.rolled_back = True
    def close(self): pass

def get_db():
    db = DBSession() # db = SessionLocal()
    print("Abriendo conexión a la base de datos")
    try:
        yield db
        # Si el path operation termina sin excepción, hacemos commit.
        db.commit()
        print("Haciendo COMMIT")
    except HTTPException as e:
        # Si es una excepción HTTP, la relanzamos
        # (El cliente causó el error, no la lógica de negocio)
        db.rollback()
        print("Haciendo ROLLBACK por HTTPException")
        raise e
    except Exception as e:
        # Si es cualquier otra excepción (ej. error 500), hacemos rollback.
        db.rollback()
        print(f"Haciendo ROLLBACK por error interno: {e}")
        # Opcionalmente, relanza el error para que FastAPI lo maneje
        raise e
    finally:
        # El bloque finally se ejecuta SIEMPRE.
        db.close()
        print("Cerrando conexión a la base de datos")

@app.get("/safe-transaction/{item_id}")
async def safe_transaction(item_id: int, db: Session = Depends(get_db)):
    if item_id == 1:
        # Esto funcionará y hará COMMIT
        return {"message": "Éxito, se hará commit"}
    if item_id == 2:
        # Esto fallará y hará ROLLBACK (error del cliente)
        raise HTTPException(status_code=404, detail="Item no encontrado")
    if item_id == 3:
        # Esto fallará y hará ROLLBACK (error del servidor)
        result = 10 / 0 
        return {}

3. Clases como Dependencias (Avanzado)

Usar una clase como dependencia es un patrón increíblemente poderoso para agrupar lógica de negocio o parámetros complejos. FastAPI inyecta dependencias en el __init__ de la clase.

Patrón avanzado: Puedes hacer que tu clase sea un "callable" (implementando __call__) para crear dependencias configurables y reutilizables.

Patrón avanzado: Puedes hacer que tu clase sea un "callable" (implementando __call__) para crear dependencias configurables y reutilizables.

Aquí, creamos un verificador de permisos que *se configura* en __init__ y *se ejecuta* en __call__. 


from fastapi import FastAPI, Depends, HTTPException, Security
from typing import List, Optional

# Simulación de un usuario y un token
class User:
    def __init__(self, username: str, scopes: List[str]):
        self.username = username
        self.scopes = scopes

# Dependencia simple que obtiene el usuario (simulada)
async def get_current_user(token: Optional[str] = Security(None)) -> User:
    # En una app real, decodificarías el token JWT
    if token == "admin_token":
        return User(username="admin", scopes=["read", "write", "admin"])
    if token == "user_token":
        return User(username="user", scopes=["read"])
    raise HTTPException(status_code=401, detail="No autenticado")

# --- La Clase de Dependencia Avanzada ---

class PermissionChecker:
    """
    Esta clase se instancia con los permisos REQUERIDOS.
    FastAPI no la llamará directamente.
    """
    def __init__(self, required_scopes: List[str]):
        self.required_scopes = required_scopes
        print(f"Checker configurado para requerir: {required_scopes}")

    """
    FastAPI llamará a este método porque `Depends`
    apuntará a una *instancia* de esta clase.
    """
    async def __call__(self, user: User = Depends(get_current_user)):
        print(f"Revisando scopes... Requeridos: {self.required_scopes}, Usuario tiene: {user.scopes}")
        for scope in self.required_scopes:
            if scope not in user.scopes:
                raise HTTPException(
                    status_code=403,
                    detail=f"Permiso insuficiente. Se requiere: '{scope}'"
                )
        return user # Opcionalmente, devuelve el usuario verificado

# --- Instanciamos nuestras dependencias configurables ---
# Nota: NO usamos Depends() aquí.
# Estamos creando las instancias que SERÁN las dependencias.
check_admin = PermissionChecker(required_scopes=["admin"])
check_read_write = PermissionChecker(required_scopes=["read", "write"])

# --- Uso ---
@app.get("/admin/dashboard")
async def get_admin_dashboard(admin_user: User = Depends(check_admin)):
    # `check_admin` es una instancia, FastAPI llama a `check_admin.__call__()`
    # `__call__` a su vez depende de `get_current_user`
    return {"message": f"Hola admin {admin_user.username}"}

@app.post("/items")
async def create_item(editor: User = Depends(check_read_write)):
    # `check_read_write` es otra instancia con diferente configuración
    return {"message": f"Item creado por {editor.username}"}

4. dependencies en el Decorador

Ya conoces las dependencias en la firma de la función (ej. db: Session = Depends(get_db)), que inyectan un valor en tu función.

en el decorador de la operación (@app.get, @app.post, etc.).

Estas dependencias se ejecutan, pero su valor de retorno no se pasa a tu función.

Caso de uso: Perfecto para validaciones de "todo o nada". Por ejemplo, verificar una cabecera X-Api-Key o un permiso que solo debe lanzar un error 403 si falla, pero no necesitas el valor de la API key en tu lógica de negocio. 


from fastapi import FastAPI, Depends, HTTPException, Header
from typing import Optional

app = FastAPI()

# Una dependencia que solo valida.
# Si tiene éxito, no devuelve nada útil (None).
# Si falla, lanza una excepción.
async def verify_api_key(x_api_key: Optional[str] = Header(None)):
    if x_api_key != "mi-api-key-secreta":
        raise HTTPException(status_code=401, detail="X-Api-Key inválida o faltante")
    print("X-Api-Key verificada")
    return None # El valor de retorno se descarta

async def log_request_metadata(user_agent: Optional[str] = Header(None)):
    print(f"Request recibido de User-Agent: {user_agent}")
    return None # El valor de retorno se descarta

# Usamos `dependencies` en el decorador
@app.get(
    "/datos-sensibles",
    dependencies=[
        Depends(verify_api_key),
        Depends(log_request_metadata)
    ]
)
async def get_sensitive_data():
    # Si el código llega aquí, es porque verify_api_key tuvo éxito.
    # Nota que no tenemos `api_key` o `user_agent` como argumento.
    # La firma de la función está limpia.
    return {"data": "información muy secreta"}

# También puedes aplicarlo a un Router entero o a la App

5. Testing y dependency_overrides

La verdadera magia de la Inyección de Dependencias se revela en el testing. El sistema Depends está diseñado para ser sobrescrito (overridden) durante las pruebas.

externo) por una versión "mock" o falsa que devuelva datos controlados.

Mejor práctica: Usa app.dependency_overrides junto con TestClient para crear pruebas unitarias rápidas, aisladas y fiables. 


# --- main.py (Tu aplicación) ---
from fastapi import FastAPI, Depends, HTTPException

app = FastAPI()

class User:
    def __init__(self, username: str, email: str):
        self.username = username
        self.email = email

# Esta es la dependencia de PRODUCCIÓN.
# En un caso real, buscaría en la BD o en un servicio externo.
async def get_current_user_from_token(token: str = Header(...)) -> User:
    print("Llamando a la dependencia de PRODUCCIÓN")
    if token == "prod_token":
        return User(username="prod_user", email="prod@example.com")
    raise HTTPException(status_code=401, detail="Token inválido")

@app.get("/users/me")
async def read_users_me(current_user: User = Depends(get_current_user_from_token)):
    return current_user

# --- test_main.py (Tu archivo de tests) ---
from fastapi.testclient import TestClient
# from .main import app, get_current_user_from_token, User # Importa desde tu app

# Esta es la dependencia de TEST.
# No hace llamadas externas, es instantánea.
async def override_get_current_user() -> User:
    print("Llamando a la dependencia de TEST (override)")
    return User(username="test_user", email="test@example.com")

# --- Aquí ocurre la magia ---
# Sobrescribimos la dependencia `get_current_user_from_token`
# con nuestra función `override_get_current_user`.
app.dependency_overrides[get_current_user_from_token] = override_get_current_user

client = TestClient(app)

def test_read_users_me():
    # No necesitamos pasar ningún token, porque la dependencia
    # que lo requería (`get_current_user_from_token`) ha sido reemplazada.
    response = client.get("/users/me")
    
    assert response.status_code == 200
    assert response.json() == {
        "username": "test_user",
        "email": "test@example.com"
    }
    # Y la dependencia original de producción NUNCA fue llamada.

# Limpiamos el override después del test si es necesario
# (Pytest lo maneja mejor con fixtures)
app.dependency_overrides = {}
